# Requirements Document

## Introduction

This document formalizes the behavioral contract of the existing Newman trend-metrics and reporting pipeline in this repository. The capability is already implemented across three cooperating pieces: the metrics-extraction script (`scripts/newman-trend-metrics.js`), the chart click-through rewriter (`scripts/link-chart-to-reports.js`), and the trend/reporting orchestration in the GitHub Actions workflow (`.github/workflows/postman-ci.yml`).

These requirements describe what the existing system does and the invariants it must preserve. They are a regression contract: every requirement names an observable behavior the current implementation already satisfies, so that future changes can be checked against them. No new functionality is introduced here.

The system under test is the public PokéAPI; request volume is kept deliberately low. There is no application code to fix in this repository. Reports are gitignored and regenerated on every run. Response time is captured only as a trend metric and is never used as a pass/fail gate.

## Glossary

- **Metrics_Extractor**: The Node.js script `scripts/newman-trend-metrics.js`, which reads a Newman JSON report and emits a GitHub Actions job summary and a benchmark-compatible metrics file.
- **Chart_Linker**: The Node.js script `scripts/link-chart-to-reports.js`, which rewrites the trend chart's click handler to open archived per-run reports.
- **CI_Pipeline**: The GitHub Actions workflow `.github/workflows/postman-ci.yml`, specifically its `run-collection` and `deploy-pages` jobs that orchestrate trend extraction and reporting.
- **Newman_Report**: The Newman JSON report (`reports/pokeapi.results.json`) produced by running the Postman collection; its `run.stats`, `run.timings`, and `run.failures` fields are consumed.
- **Metrics_File**: The benchmark-action-compatible output file (benchmark-action `customSmallerIsBetter` format): a JSON array of objects each having `name`, `unit`, and `value` fields.
- **Job_Summary**: The Markdown table written to the GitHub Actions `$GITHUB_STEP_SUMMARY` file.
- **Verdict**: The pass/fail result displayed in the Job_Summary, derived from all categories of Newman failure.
- **Trend_Chart**: The HTML chart generated by benchmark-action/github-action-benchmark, served from the published site and plotting metric values over time.
- **Archived_Report**: A per-run htmlextra report persisted on the `gh-pages` branch under `reports/<commit-sha>.html`.
- **Link_Prefix**: The relative URL prefix the Chart_Linker uses to reference Archived_Reports from a given chart copy.
- **Pages_Site**: The assembled static site published via the official GitHub Pages deployment.
- **Default_Branch**: The `main` branch.

## Requirements

### Requirement 1: Metrics extraction from the Newman report

**User Story:** As a QA engineer, I want a benchmark-compatible metrics file derived from the Newman report, so that run metrics can be charted over time.

#### Acceptance Criteria

1. WHEN the Metrics_Extractor is invoked with a readable, parseable Newman_Report path and an output path, THE Metrics_Extractor SHALL write a Metrics_File containing exactly three entries, in order, named `Failed assertions`, `Failed requests`, and `Avg response time`.
2. THE Metrics_Extractor SHALL set the `Failed assertions` entry to a string `unit` of `count` and an integer `value` equal to `run.stats.assertions.failed` from the Newman_Report.
3. THE Metrics_Extractor SHALL set the `Failed requests` entry to a string `unit` of `count` and an integer `value` equal to `run.stats.requests.failed` from the Newman_Report.
4. THE Metrics_Extractor SHALL set the `Avg response time` entry to a string `unit` of `ms` and an integer `value` equal to `run.timings.responseAverage` from the Newman_Report rounded half-up to the nearest integer.
5. WHERE a consumed field (`run.stats.assertions`, `run.stats.requests`, or `run.timings.responseAverage`) is absent from the Newman_Report, THE Metrics_Extractor SHALL use a default of zero for that field.

### Requirement 2: Smaller-is-better metric contract

**User Story:** As a QA engineer, I want every trend metric to point in the same direction, so that a single chart orientation is unambiguous.

#### Acceptance Criteria

1. THE Metrics_Extractor SHALL emit every metric in the Metrics_File as a quantity where a numerically smaller `value` represents a better outcome.
2. THE Metrics_Extractor SHALL represent assertion health as a failed-assertion count rather than a passed-assertion count, so that the metric decreases as the run improves.
3. THE Metrics_Extractor SHALL write the Metrics_File as a JSON array in which each element contains a string `name` field, a string `unit` field, and a numeric `value` field.

### Requirement 3: All-failures verdict rule

**User Story:** As a QA engineer, I want the job-summary verdict to reflect every category of Newman failure, so that a run is never mislabeled as passing when a request or script error occurred.

#### Acceptance Criteria

1. WHILE the `GITHUB_STEP_SUMMARY` environment variable is present and non-empty, THE Metrics_Extractor SHALL append to the file it names a Job_Summary Markdown table with one row each for the Verdict, passed assertions over total assertions with pass rate, failed assertions, failed requests over total requests, and average response time.
2. IF `run.stats.assertions.failed` is greater than zero, OR `run.stats.requests.failed` is greater than zero, OR `run.failures.length` is greater than zero, THEN THE Metrics_Extractor SHALL set the Verdict to fail.
3. IF `run.stats.assertions.failed` equals zero, AND `run.stats.requests.failed` equals zero, AND `run.failures.length` equals zero, THEN THE Metrics_Extractor SHALL set the Verdict to pass.
4. WHERE `run.failures.length` is greater than zero, THE Metrics_Extractor SHALL include a run-level failure count row in the Job_Summary so that a failing Verdict with zero failed assertions is explained.
5. IF the `GITHUB_STEP_SUMMARY` environment variable is absent or empty, THEN THE Metrics_Extractor SHALL omit the Job_Summary and still write the Metrics_File.

### Requirement 4: Metrics extractor CLI argument and exit-code contract

**User Story:** As a pipeline author, I want the Metrics_Extractor to signal invalid invocation clearly, so that a misconfigured step fails fast.

#### Acceptance Criteria

1. IF the Metrics_Extractor is invoked with fewer than two positional arguments (a results path argument and a metrics output path argument), THEN THE Metrics_Extractor SHALL write a usage message to standard error, SHALL NOT create or modify the metrics output file, and SHALL exit with code 2.
2. IF the Newman_Report at the provided results path cannot be read, THEN THE Metrics_Extractor SHALL write an error message to standard error indicating the path could not be read, SHALL NOT create or modify the metrics output file, and SHALL exit with code 2.
3. IF the Newman_Report at the provided results path cannot be parsed as JSON, THEN THE Metrics_Extractor SHALL write an error message to standard error indicating the report could not be parsed, SHALL NOT create or modify the metrics output file, and SHALL exit with code 2.
4. WHEN the Metrics_Extractor completes successfully, THE Metrics_Extractor SHALL write the metrics output file to the provided metrics output path and SHALL exit with code 0.

### Requirement 5: Chart click-through rewriting to archived reports

**User Story:** As a maintainer, I want clicking a trend data point to open that run's archived report, so that I can inspect the full results behind a point.

#### Acceptance Criteria

1. WHEN the Chart_Linker is invoked with a chart HTML path and a reports directory, THE Chart_Linker SHALL collect the set of commit SHAs by reading the reports directory, selecting only filenames ending in `.html`, and taking each selected filename with its `.html` suffix removed as one commit SHA.
2. WHEN the Chart_Linker rewrites the chart click handler, THEN for a data point whose commit SHA exactly matches a collected commit SHA, THE Chart_Linker SHALL make the handler open the Archived_Report at the concatenation of the Link_Prefix, the data point's commit SHA, and `.html`.
3. WHEN the Chart_Linker rewrites the chart click handler, THEN for a data point whose commit SHA matches no collected commit SHA, THE Chart_Linker SHALL make the handler open the data point's `commit.url`.
4. WHERE no Link_Prefix argument is provided, THE Chart_Linker SHALL use the Link_Prefix `./reports/`.
5. WHEN the CI_Pipeline invokes the Chart_Linker on a chart copy served one directory deep, THE CI_Pipeline SHALL pass the Link_Prefix `../reports/` so that links resolve to the shared archive.

### Requirement 6: Chart linker graceful fallbacks

**User Story:** As a maintainer, I want the Chart_Linker to degrade gracefully, so that a missing archive or an upstream template change never breaks the published chart.

#### Acceptance Criteria

1. IF the reports directory cannot be read, THEN THE Chart_Linker SHALL leave the chart HTML byte-for-byte unchanged, SHALL write a message to standard output indicating the chart was left unchanged, and SHALL exit with code 0.
2. WHEN the chart click handler is present in its exact expected form, THE Chart_Linker SHALL replace every exact occurrence of that handler with the rewritten handler that prefers Archived_Reports, and SHALL exit with code 0.
3. WHERE the exact handler form is absent but a whitespace-tolerant match of the handler succeeds, THE Chart_Linker SHALL replace the matched handler with the rewritten handler that prefers Archived_Reports, and SHALL exit with code 0.
4. IF neither the exact handler form nor the whitespace-tolerant match is found, THEN THE Chart_Linker SHALL leave the chart HTML byte-for-byte unchanged, SHALL write a message to standard error indicating the handler was not found, and SHALL exit with code 0.

### Requirement 7: Chart linker CLI argument and exit-code contract

**User Story:** As a pipeline author, I want the Chart_Linker to signal invalid invocation clearly, so that a misconfigured step fails fast.

#### Acceptance Criteria

1. IF the Chart_Linker is invoked with fewer than two positional arguments (a chart HTML path argument and a reports directory argument), THEN THE Chart_Linker SHALL write a usage message to standard error, SHALL NOT modify the chart HTML, and SHALL exit with code 2.
2. IF the chart HTML at the provided path cannot be read, THEN THE Chart_Linker SHALL write an error message to standard error indicating the path could not be read, SHALL NOT modify the chart HTML, and SHALL exit with code 2.

### Requirement 8: Trend steps run always and never swallow the authoritative result

**User Story:** As a QA engineer, I want trend extraction and job summary to run even on a red run without changing the pass/fail result, so that failing runs still contribute data while the authoritative verdict is preserved.

#### Acceptance Criteria

1. THE CI_Pipeline SHALL run the trend metrics extraction step and the job summary step regardless of whether any prior step in the job succeeded or failed, so that a failing run still produces one trend data point and one job summary.
2. THE CI_Pipeline SHALL execute the trend metrics extraction step and the job summary step as steps separate from the collection-run step, and SHALL leave the collection-run step's exit code unchanged by those steps.
3. IF the collection-run step records at least one failed request, at least one failed assertion, or at least one run-level failure, THEN THE CI_Pipeline SHALL set the job's authoritative result to fail.
4. IF the collection-run step records zero failed requests, zero failed assertions, and zero run-level failures, THEN THE CI_Pipeline SHALL set the job's authoritative result to pass.

### Requirement 9: Trend update and deploy gated to pushes on the default branch

**User Story:** As a maintainer, I want the published trend and site to update only on default-branch pushes, so that pull requests and feature branches do not pollute the published history.

#### Acceptance Criteria

1. IF the triggering event is a push whose target ref is the Default_Branch, THEN THE CI_Pipeline SHALL append the current run's metrics as one data point to the `gh-pages` branch and update the Trend_Chart.
2. IF the triggering event is not a push whose target ref is the Default_Branch, THEN THE CI_Pipeline SHALL skip the trend-update step and skip the deploy-pages job, leaving the published trend and Pages_Site unchanged.
3. THE CI_Pipeline SHALL configure the trend-update step with an alert threshold of 200 percent relative to the previous data point, with comment-on-alert enabled and fail-on-alert disabled, so that a regression of 200 percent or more is flagged by a comment without changing the job's authoritative result.

### Requirement 10: Per-run report archival with retry

**User Story:** As a maintainer, I want each run's report archived durably on the gh-pages branch, so that trend data points link to persistent reports despite stateless runners and branch contention.

#### Acceptance Criteria

1. WHEN the deploy-pages job runs on a push whose target ref is the Default_Branch, THE CI_Pipeline SHALL archive the current run's htmlextra report on the `gh-pages` branch at the path `reports/<commit-sha>.html`, where `<commit-sha>` is the triggering commit SHA.
2. IF a push of the archived report to `gh-pages` is rejected because the branch advanced concurrently, THEN THE CI_Pipeline SHALL re-fetch `gh-pages`, reset to the latest `gh-pages`, re-apply the archived report, and retry the push, repeating this sequence until the push succeeds or 3 total attempts have been made.
3. WHERE an archived report already exists on `gh-pages` for the triggering commit SHA with identical content, THE CI_Pipeline SHALL leave the existing archive unchanged and SHALL NOT create an additional commit.

### Requirement 11: Site assembly layout

**User Story:** As a user of the published site, I want a predictable layout of chart and reports, so that I can reach the trend, the latest report, and archived reports from stable URLs.

#### Acceptance Criteria

1. WHEN the deploy-pages job assembles the Pages_Site, THE CI_Pipeline SHALL place the Trend_Chart at the site root path `/`.
2. WHEN the deploy-pages job assembles the Pages_Site, THE CI_Pipeline SHALL place the latest run's htmlextra report at `/report/`.
3. WHEN the deploy-pages job assembles the Pages_Site, THE CI_Pipeline SHALL place every Archived_Report found on `gh-pages` at `/reports/`.
4. WHEN the deploy-pages job assembles the Pages_Site, THE CI_Pipeline SHALL place a second copy of the Trend_Chart at `/trend/` for backward compatibility.
5. IF the latest run's htmlextra report is unavailable during assembly, THEN THE CI_Pipeline SHALL place a placeholder page at `/report/` that links back to the Trend_Chart at `/`.
6. WHEN the deploy-pages job assembles the Pages_Site, THE CI_Pipeline SHALL rewrite the root chart copy's click handler with Link_Prefix `./reports/` and rewrite the `/trend/` chart copy's click handler with Link_Prefix `../reports/`.

### Requirement 12: Publication via the official Pages deployment

**User Story:** As a maintainer, I want the site published through the official GitHub Pages deployment, so that each run reliably triggers a Pages rebuild.

#### Acceptance Criteria

1. WHEN the deploy-pages job publishes the Pages_Site, THE CI_Pipeline SHALL deploy it through the official GitHub Pages deployment action rather than through a GITHUB_TOKEN push to a branch.
